# Workshop SDK for auto-wp's Rust layer — specification

This document specifies `creusot`, a Workshop SDK that packages the
Creusot toolchain auto-wp's Rust skills need (`creusot`,
`creusot-monitoring`, `creusot-sl`, `time-loop`, and `creusot-launch` once
it is written: auto-wp.md §4.3.7, roadmap step 1). It replaces the
hour-long, hand-run build of `tests/rust/provision.sh` step 2 and of
`creusot/references/install.md` (Creusot's `./INSTALL`) with a prebuilt,
versioned unit that a workshop installs in minutes.

It is the Rust counterpart of `workshop-autowp-c-base-spec.md` (the C
spec), whose §1 (Workshop in brief) and §2 (common decisions) apply here
unchanged and are not repeated. The C spec's §11 records what building the
three other SDKs taught, and this design reuses it: an opam root built at a
fixed `/opt/autowp-<name>` path and linked to `$SDK` at run time, a
hand-written environment instead of `opam env`, `check-health` through
`runuser`, and per-user state seeded into `mount` plugs, as `lean`
does for `~/.elan`. The name of this file keeps the `autowp-rust-base` of the
LXD base container that `tests/rust/provision.sh` builds and this SDK
supersedes.

`rocq` and `lean` are language-independent and combine with
`creusot` in the same workshop; `frama-c-sdk` is not needed for Rust.

The facts about Creusot below come from its sources at the pinned commit
(`creusot-install/src/main.rs`, `creusot-setup/src/{lib,tools,tools_versions_urls}.rs`,
`cargo-creusot/src/{main,config,new,why3find_wrapper,why3_launcher}.rs`,
`creusot-deps.opam`, read on 2026-10-31), from the host installation of the
same commit, from `creusot/references/install.md`, and from `../use-creusot/`,
where Creusot was used on a 241-file corpus and on the Lace boot loader. The
review of the first draft is `workshop-autowp-rust-base-spec-report.md`; its
findings are integrated here.

## 1. What Creusot's `./INSTALL` does

`./INSTALL` runs `cargo run --bin creusot-install`, which:

| Step | Result | Where |
|---|---|---|
| Why3 | a **local opam switch** with OCaml 5.3.0, Why3 `git-05bf4ddf` (1.8.2+git) and why3find `git-0f054b93` (Creusot's fork); `why3` and `why3find` linked into `bin/` | `$DATA/_opam`, `$DATA/bin` |
| prelude | Creusot's Why3 library, generated by `prelude-generator` | `$DATA/share/why3find/packages/creusot/` |
| `cargo-creusot` | `cargo install --path cargo-creusot` | `$CARGO_HOME/bin` |
| `creusot-rustc` | `cargo install --root`, built with the nightly in `rust-toolchain` (`nightly-2026-08-03`, components `rustfmt`, `rustc-dev`, `llvm-tools`) | `$DATA/toolchains/nightly-2026-08-03/bin` |
| provers | release binaries, downloaded to `~/.cache/creusot` and checked against the sha256 in `creusot-setup/src/tools_versions_urls.rs`: Alt-Ergo 2.6.4 (musl), Z3 5.3.2 (glibc 2.39), CVC4 1.8, CVC5 1.4.1 (static, GPL build); `--external <tool>` links a tool found on `PATH` instead | `$DATA/bin` |
| config | `why3find.json` (copied by `cargo creusot new`), `creusot_why3.conf` (the prover commands, by bare name: `alt-ergo`, `z3`, `cvc4`, `cvc5`) | `$DATA` |
| user config | `~/.config/creusot/why3.conf` (`running_provers_max`), written if missing by runs that reach the prove stage and by `cargo creusot why3`; read only by `cargo creusot why3 ide|replay` | `$XDG_CONFIG_HOME/creusot` |
| cargo config | `cargo creusot config --update`: `[patch.crates-io] creusot-std = { path = "<checkout>/creusot-std" }`, the rest of the file kept | `$CARGO_HOME/config.toml` |

The opam switch also gets `why3-ide`, unless the opam variable
`in-creusot-ci` is defined (`creusot-deps.opam`: `!?in-creusot-ci`).

`$DATA` is `$CREUSOT_DATA_HOME` when set, otherwise `~/.local/share/creusot`;
every path of `creusot-install` and `cargo-creusot` honours it. At run time:

- `cargo creusot` is an external Cargo subcommand. It runs `cargo check`
  with `RUSTUP_TOOLCHAIN=nightly-2026-08-03`,
  `RUSTC=$DATA/toolchains/…/bin/creusot-rustc` and
  `CARGO_TARGET_DIR=target/creusot`. `creusot-rustc` is linked against the
  nightly's `librustc_driver`, which it finds only through the
  `LD_LIBRARY_PATH` that rustup's proxy sets (`ldd` on the host: "not
  found"). So **rustup and that nightly must be present**.
- For `why3find` and `why3` it prepends `$DATA/bin` to its children's
  `PATH`, and sets `WHY3CONFIG=$DATA/creusot_why3.conf`; `why3find prove`
  does not read `~/.config/creusot/why3.conf`.
- `cargo creusot config` (no option) only checks the patch and **always
  exits 0**; it prints `No problems found.` when the path is current. The
  path it expects is the parent of `cargo-creusot`'s compile-time manifest
  directory (or `$CREUSOT_PATH`), i.e. the checkout it was built from.
- `cargo creusot version` lists six tools, but this commit's CVC5 detector
  expects `This is cvc5 version`, and cvc5 1.4.1 prints `cvc5 1.4.1 […]`, so
  its line reads `cvc5 bad CVC5 version: cvc5 1.4.1 [git …]`; `install.md`
  §4's table shows the version, not the line.

The `[patch]` path needs the **whole Creusot source tree**: `creusot-std`
depends on `../creusot-std-proc`, which depends on `../pearlite-syn`, and all
three use workspace inheritance (`version.workspace = true`). On this host
the installed `$DATA` is 1.4 GB and the full nightly 2.4 GB, of which
`lib/rustlib/x86_64-unknown-linux-gnu/lib` (where `rustc-dev`'s rlibs live)
is 967 MB.

Three properties shape the SDK:

1. The opam switch embeds absolute paths (C spec §2): build `$DATA` at a
   fixed path.
2. `cargo creusot` writes only to `$XDG_CONFIG_HOME/creusot/`, to
   `$CARGO_HOME`, and inside the project: `target/creusot/`, `verif/` (the
   Coma output), `_creusot_erasure/`, the `.why3find/` cache, and on
   `new`/`init` `why3find.json` and `.gitignore`. `$DATA` holds no cache, so
   `$DATA` and the source tree can be read-only (§4.3 confirms it). The
   overlay `.gitignore` the skills generate must cover the project-side
   entries.
3. rustup and `$CARGO_HOME` must stay writable for the user: the crate
   under study may need another toolchain (its own `rust-toolchain.toml`) or
   a target (Lace targets `x86_64-unknown-uefi`, `use-creusot/lace-workflow.md`),
   and Cargo downloads dependencies into `$CARGO_HOME/registry`.

### 2.1 Alt-Ergo

Alt-Ergo 2.6.4, the version Creusot's `creusot_why3.conf` drives
(`alt_ergo_26`), is distributed in its GitHub and opam releases under the
*OCamlPro Non-Commercial Purpose License, version 1* (`LICENSE.md` at tag
`v2.6.4`; Apache-2.0 only for Alt-Ergo Club Gold members; the free
`alt-ergo-free`, CeCILL-C, stops at 2.4.3). Its terms:

- use is allowed "solely for research", and excludes any use "in
  connection with a product or service which is sold, offered for sale,
  licensed, leased, loaned, or rented, or used in a profit-making context";
- copying and redistribution are allowed without fee for that purpose, if
  the copyright notice and the licence go with every copy; each recipient
  gets the same terms, and no further restriction may be added;
- commercial use needs a licence negotiated with OCamlPro
  (contact@ocamlpro.com).

**Decision (2026-10-31): Alt-Ergo is bundled**, as in `frama-c-sdk`
(C spec §8). The SDK is free and not sold, but the restriction is on use, so
it passes to every user of the SDK. The SDK therefore:

- ships OCamlPro's `LICENSE.md` and the licence text in
  `$SDK/share/licenses/alt-ergo/` (from `files/share/licenses/alt-ergo/`);
- says "Alt-Ergo 2.6.4: OCamlPro Non-Commercial Purpose License, research
  use only" in its `description`, in `sdks/README.md`, and in the Workshop
  quick start of `templates/rust/README.md`;
- keeps the upstream prover set-up unchanged: `creusot_why3.conf` and
  `why3find.json` use Alt-Ergo, Z3, CVC4 and CVC5.

A user whose use is commercial removes Alt-Ergo from the strategy in their
project's `why3find.json` (Z3, CVC4 and CVC5 remain) or obtains a licence
from OCamlPro. Whether the SDK Store accepts a component under this licence
is checked before publishing (open point 5).

## 3. Build (`sdkcraft.yaml` and `override-build`)

```yaml
name: creusot
version: "0.15.0-f15b985"
title: Creusot for auto-wp
summary: Creusot at f15b985 with its Rust nightly, Why3, why3find and provers
description: |
  The Creusot toolchain the auto-wp Rust skills expect: cargo-creusot and
  creusot-rustc built at commit f15b985, the Rust nightly-2026-08-03 they
  need, Creusot's Why3 and why3find switch, Alt-Ergo, Z3, CVC4 and CVC5,
  and the Creusot sources that creusot-std is patched to.
  Alt-Ergo 2.6.4 is bundled under the OCamlPro Non-Commercial Purpose
  License: research use only, see share/licenses/alt-ergo/ in the SDK.
license: LGPL-2.1-or-later      # Creusot's; the bundle's other licences in the README
platforms:
  noble:
    build-on: [ubuntu@24.04:amd64]
    build-for: [ubuntu@24.04:amd64]
  resolute:
    build-on: [ubuntu@26.04:amd64]
    build-for: [ubuntu@26.04:amd64]

plugs:
  rustup:
    interface: mount
    workshop-target: /home/workshop/.rustup
  cargo:
    interface: mount
    workshop-target: /home/workshop/.cargo

parts:
  creusot:
    plugin: nil
    source: https://github.com/creusot-rs/creusot.git
    source-type: git
    source-commit: f15b98593980ce264a681a275b204891d03e9608
    build-packages: [opam, build-essential, pkg-config, m4, unzip, curl,
                     ca-certificates, git, rsync, autoconf, libgmp-dev,
                     zlib1g-dev]
    override-build: |
      …the steps below…
  config:
    plugin: dump
    source: files            # profile, Alt-Ergo's licence files, the smoke project
```

The platforms are those the three other SDKs build for since 2026-10-31
(C spec §11). The Z3 binary needs glibc 2.39, which both bases have.
`autoconf` is a build dependency of Why3 from git (`conf-autoconf`); the
GTK packages are not needed thanks to `in-creusot-ci`.

Steps of `override-build`, with `R=/opt/creusot`:

1. **Paths.** `rm -rf "$R"`, as `rocq` does. `export
   RUSTUP_HOME=$R/rustup CARGO_HOME=$R/cargo CREUSOT_DATA_HOME=$R/data
   OPAMROOT=$R/opam`; `PATH=$R/bin:$CARGO_HOME/bin:$PATH` (`$R/bin` because
   `cargo-creusot` moves there in step 5 and the later steps still call it). Copy the part's source
   (the build directory, `$CRAFT_PART_BUILD`) to `$R/src/creusot` and build
   there: `cargo-creusot` records the checkout it is built from (§1), so the
   tree must already be at its final path.
2. **Rust.** Download the pinned `rustup-init`, check its sha256, run
   `rustup-init -y --no-modify-path --profile minimal --default-toolchain none`,
   then install the nightly explicitly rather than relying on rustup's
   auto-install (removed in 1.28.0, restored in 1.28.1, and switchable off):
   `rustup toolchain install nightly-2026-08-03 --profile minimal
   -c rustfmt -c rustc-dev -c llvm-tools` and **`rustup default
   nightly-2026-08-03`**. Without a default, the `cargo` proxy refuses to run
   outside the checkout ("rustup could not choose a version of cargo to
   run"), and `cargo creusot` is launched through that proxy.
3. **opam.** `opam init --disable-sandboxing -y --bare`;
   `opam var --global in-creusot-ci=true`, so `creusot-deps.opam` skips
   `why3-ide` and its GTK dependencies.
4. **Creusot.** `./INSTALL`, with no `--external` option: the four provers
   are the pinned, checksummed downloads.
5. **Take out `cargo-creusot`**: move it from `$CARGO_HOME/bin` to `$R/bin`.
6. **Checks** (the build fails otherwise):
   - `git rev-parse HEAD` of `$R/src/creusot` is the pinned commit (before
     `.git/` is pruned in step 7);
   - `cargo creusot version` gives `cargo-creusot 0.15.0-dev` and lists Why3
     `1.8.2`, why3find `v1.3.0`, Alt-Ergo `2.6.4`, Z3 `5.3.2`, CVC4 `1.8` and
     `cvc5 1.4.1` (§1 for the CVC5 line);
   - in a directory with no `Cargo.toml` above it, `cargo creusot new smoke`
     then `cargo creusot` proves the generated `add_one`.
7. **Prune**: `$R/src/creusot/target/` (the build of Creusot itself, many
   GB), `$R/src/creusot/.git/`, opam's download cache and build directories,
   rustup's `downloads/` and `tmp/`. Then remove `rustc-dev` and `llvm-tools`
   from the nightly and rerun the proof **in a fresh project**
   (`cargo creusot new smoke2`): rerunning in `smoke` would reuse
   `target/creusot/`, `verif/` and `.why3find/`, never execute
   `creusot-rustc`, and prove whatever the toolchain. Run `cargo test` there
   as well. If both pass, ship without the two components
   (`librustc_driver` is in the `rustc` component); if not, reinstall them
   and record why.
8. **Seeds.**
   - The **registry seed** is built in a fresh home, so it does not hold the
     192 crates of Creusot's own build: `CARGO_HOME=$R/seed/cargo`, with a
     `config.toml` holding only the `[patch]` entry (without it, Cargo looks
     for `creusot-std 0.15.0-dev` on crates.io and fails); `cargo creusot new
     seed`, `cargo generate-lockfile` and `cargo fetch` in it. Keep the
     project's `Cargo.lock` as `$R/share/smoke/Cargo.lock`; delete the seed's
     `config.toml` and `registry/src/` (Cargo re-extracts from
     `registry/cache/`).
   - The **rustup seed**: move `$CARGO_HOME/bin` (rustup's proxies, now
     without `cargo-creusot`) into `$R/seed/cargo/bin`, and `$RUSTUP_HOME` to
     `$R/seed/rustup/`. Drop the build's `$CARGO_HOME/config.toml`: each user
     gets their own (§4.2).
9. Copy `$R` into `$CRAFT_PART_INSTALL`.

`creusot` needs no `prepare.sh`: nothing comes from auto-wp's
`templates/`.

## 4. Runtime

### 4.1 `setup-base` (root)

- `ln -sfn "$SDK" /opt/creusot`, so the opam switch, the
  `creusot-rustc` path and the `creusot-std` path resolve (C spec §2).
- apt: `build-essential` (the linker Cargo calls), `pkg-config`, `git`,
  `curl`, `ca-certificates`, `ripgrep`, `python3`, `libgmp10` and `zlib1g`
  (Why3 and why3find link them, through zarith and camlzip).
- `install -m 644 "$SDK/creusot.profile" /etc/profile.d/creusot.sh`,
  as the three other SDKs do. The profile, with `$HOME` left unexpanded and
  the idempotent `case ":$PATH:"` pattern of the other profiles:
  - `CREUSOT_DATA_HOME=/opt/creusot/data`;
  - `PATH` gains `/opt/creusot/bin` (`cargo-creusot`), then
    `$HOME/.cargo/bin` (rustup's proxies). This does not make the SDK's `cargo-creusot`
    unshadowable: Cargo searches `$CARGO_HOME/bin` for subcommands first, so
    a `cargo install cargo-creusot` by the user wins; health check 1 detects
    it;
  - `$DATA/bin` (`why3`, `why3find`, the provers) is **not** on `PATH`:
    `cargo-creusot` adds it for its own children, and in a workshop that
    also has `frama-c-sdk`, it would collide with that SDK's `why3`, `z3`
    and `alt-ergo` wrappers;
  - `CREUSOT_SDK_SRC=/opt/creusot/src/creusot` and
    `CREUSOT_SDK_COMMIT=f15b985`, which the Rust toolchain check records
    (auto-wp.md, the Rust toolchain check row);
  - `RUSTUP_TOOLCHAIN` is **not** set: it would override the crate's own
    `rust-toolchain.toml` (§1 property 3).

### 4.2 `setup-project` (`workshop`)

- **Seed `~/.rustup` and `~/.cargo`** (the two mount plugs) from
  `$SDK/seed/`, with the guard `lean` uses (copy when the nightly is
  not there yet), but copying with `cp -a --update=none` rather than
  `lean`'s plain `cp -a`, so a user's own toolchains, targets,
  `config.toml` and registry entries are kept. Not `cp --no-clobber`: with
  Ubuntu 24.04's coreutils 9.4 it exits non-zero when it skips a file
  (coreutils 9.2 to 9.4), which aborts the hook on every refresh that ships
  a new nightly; `--update=none` (coreutils ≥ 9.3, both bases) has a stable
  exit status.
- **`rustup default nightly-2026-08-03`**, unconditionally: after a refresh
  to a revision with another nightly, the user's kept `settings.toml` would
  otherwise still name the old one. The crate under study keeps whatever its
  own `rust-toolchain.toml` asks for, downloaded into the mount. An old
  nightly left by a previous revision is not removed (open point 1).
- **`/opt/creusot/bin/cargo-creusot creusot config --update`**
  (called directly, not through the `cargo` proxy: `cargo-creusot` skips
  its first argument), which writes the `[patch.crates-io]` entry pointing at
  `/opt/creusot/src/creusot/creusot-std` into `~/.cargo/config.toml`,
  keeping the rest of the file. It points there because the build ran at
  that path (§1, §3 step 1). This replaces the "keep the checkout where it
  is" rule of `install.md` §3: the path is fixed by the SDK, and a refresh
  to another commit updates it.

`~/.config/creusot/why3.conf` is not created here: `cargo creusot` writes
it when it first proves, and only `cargo creusot why3 ide|replay` reads it.

### 4.3 `check-health`

As in the other SDKs, each check runs as `workshop` through
`runuser -u workshop -- bash -lc '…'`; `bash -l` is what makes
`/etc/profile.d/creusot.sh` apply, and `runuser` sets
`HOME=/home/workshop`. The checks are kept short: the smoke proof compiles
`creusot-std` with `creusot-rustc` and takes minutes, so it runs in
`sdks/test-sdk.sh` (§6), not on every launch and refresh.

1. `cargo creusot version` (through the proxy) gives `cargo-creusot
   0.15.0-dev` on its first line and lists the tools of §2; and
   `command -v cargo-creusot` is `/opt/creusot/bin/cargo-creusot`,
   with no `~/.cargo/bin/cargo-creusot` shadowing it (§4.1).
2. `cargo creusot config` prints `No problems found.` (it exits 0 in every
   case, §1).
3. `rustup run nightly-2026-08-03
   /opt/creusot/data/toolchains/nightly-2026-08-03/bin/creusot-rustc
   --version` runs: the nightly is installed and `librustc_driver` loads.

Any failure sets `error` with the failing command's output; the launch then
aborts (C spec §11). A write into `$SDK` needs no check of its own: `$SDK` is
root-owned, so a write fails and surfaces in the test proofs.

## 5. What `../use-creusot/` adds

`use-creusot` is the methodology the Rust skills were taken from. What it
shows about the environment, and what the SDK does with it:

- **Its pinned nightly differs.** `use-creusot/Makefile` and
  `compile-check.sh` type-check the corpus with `rustc +nightly-2026-04-21`,
  presumably the nightly of the Creusot it was run with (its README records
  no commit); auto-wp pins `f15b985` and `nightly-2026-08-03`. The SDK ships
  one nightly, Creusot's; a skill that type-checks stripped code uses the
  SDK's nightly (`TOOLCHAIN=` in that Makefile), never a hard-coded older
  one.
- **Faithfulness gate.** `use-creusot/monitor-check.sh` calls a
  `strip-creusot` binary from `/tmp/strip-creusot/`, whose source was never
  committed. auto-wp's `creusot-launch`, still to be written, is to ship its
  own stripping script (auto-wp.md, Rust checks); the SDK does not provide a
  substitute. Once that script exists, its dependencies (if any beyond the
  nightly) go into `setup-base` (open point 3).
- **Lace needs targets and offline work.** Lace targets
  `x86_64-unknown-uefi`, and `use-creusot/lxc-usage.md` ran its agents in a
  container with no network. Hence a writable `~/.rustup` (a
  `rustup target add` must work) and the registry seed: with
  `CARGO_NET_OFFLINE=true` and the shipped `Cargo.lock`, a smoke project
  proves without crates.io. Without `CARGO_NET_OFFLINE`, Cargo still asks
  the index, and `[net] offline = true` in the user's `config.toml` would
  break every real crate, so the SDK sets neither by default. A crate's own
  dependencies still need the network once, or a vendored copy in the
  project.
- **Mutation probe.** `creusot-sl`'s gate C perturbs the code and requires
  the proof to break. The SDK test (§6) does the same on a one-line
  function, so a toolchain that proves everything (a broken prover set-up
  that reports `Valid` by mistake) fails the test.
- **Workspace pitfall.** `cargo creusot new` writes `why3find.json` next to
  the nearest parent `Cargo.toml`
  (`templates/rust/skills/creusot-monitoring/bugs-to-report/20260616-1716-creusot-new-silent-skip-in-workspace.md`).
  The tests create their projects under `/tmp`, never under `/project`,
  which may hold the crate under study.

## 6. Tests

`sdks/test-sdk.sh creusot`, on both bases (`BASE=ubuntu@24.04` and
`BASE=ubuntu@26.04`), after `make sdk-creusot` (`sdkcraft try`). Projects are
created with `mktemp -d` under `/tmp`.

| Check | Passes when |
|---|---|
| `creusot.health` | the workshop reaches `ready`, with the SDK tracked from the try area |
| `creusot.tools` | `cargo creusot version` lists the tools of §2; `rustc +nightly-2026-08-03 --version` runs; `/opt/creusot/data/bin/why3 --version` is 1.8.2 (by path: `$DATA/bin` is not on `PATH`, §4.1) |

## 10. Open points

1. **Size.** Before pruning: 1.4 GB of `$DATA` and 2.4 GB of nightly, of
   which 967 MB is `rustc-dev`'s rlibs. Step 7's fresh-project experiment
   decides whether `rustc-dev` and `llvm-tools` can go; the packed size is
   measured by the first build. An old nightly left in `~/.rustup` by a
   previous revision is not cleaned up.
2. **Read-only `$DATA`.** Creusot's sources show no write under
   `$CREUSOT_DATA_HOME` at run time (§1 property 2); the test proofs confirm
   it, since `$SDK` is root-owned. If one does write, that directory moves
   to a mount plug.
3. **Stripping script.** What `creusot-launch`'s faithfulness script needs
   at run time, once written (§5).
4. **Other Creusot commits.** Projects pinned to another commit (as
   `use-creusot` was) need another SDK revision or a hand-built Creusot;
   one SDK revision ships one commit. Whether to keep older revisions on
   their own tracks depends on how often the skills move commits.
5. **Alt-Ergo and the SDK Store.** Whether the store accepts a component
   under a non-commercial licence (§2.1); if not, the published revision
   leaves Alt-Ergo out and keeps it in `try` builds.
6. **arm64.** `tools_versions_urls.rs` has arm64 Linux binaries for Z3 and
   CVC5 but none for Alt-Ergo and CVC4; an arm64 build would need
   `--external` for both.
7. **`why3 ide`.** Building without `why3-ide` drops Creusot's
   `cargo creusot why3 ide` launcher. The skills do not use it (they run
   headless); if a user wants it, it needs GTK and a display, which the
   workshop does not have by default.
8. **Hook run time.** Whether Workshop bounds a hook's run time is not in
   the documentation read; `check-health` is kept to seconds (§4.3) either
   way.
9. **Upstream nit.** `cargo creusot version`'s CVC5 detector does not
   recognise cvc5 1.4.1's output (§1); worth a report under
   `creusot-monitoring/bugs-to-report/`.

## 11. Implementation and test results (2026-11-01)

The SDK is in `sdks/creusot/` (`sdkcraft.yaml`, `hooks/`, `files/`),
with its checks in `sdks/test-sdk.sh` and the target `make sdk-creusot`;
`make test-sdks` runs the four SDKs together. Tools: `sdkcraft` 0.9.4,
`workshop` 0.9.9, LXD 6.10.1.

**Checked on the host first** (the same Creusot commit, installed by hand):
the `cargo creusot version` lines the checks match (`alt-ergo 2.6.4`,
`cvc5 bad CVC5 version: cvc5 1.4.1 …`); a proof exits 0 and prints
`Proved (verif/smoke_rlib/add_one.coma) ✔`, in about a minute, mostly
compiling `creusot-std`; the mutant of §6 exits 1 with `proof failed`;
`cargo creusot config` prints `No problems found.`; a registry seed made with
`cargo fetch` in a fresh `CARGO_HOME` is 22 MB, 4.4 MB without

The shipped `Cargo.lock` names its package, so the seed project and the
test projects are all called `smoke`.

**Differences from the design above:** none of substance. The `rustup-init`
pinned is 1.29.2. The proof checks capture `cargo creusot`'s output in a
variable before matching it, because `… | grep -q` under `pipefail` can
fail on the writer's SIGPIPE.
