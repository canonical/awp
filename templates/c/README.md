## Quick start

The campaign runs for days without asking for permission, so run the agent
harness in a container. The agent can then change only the container and
`{{DIR}}`, which is mounted into it: not your other files, not your SSH keys,
not your agent login. There are three ways to get that container; follow one:

- **A. Workshop (Linux).** The container is a
  [Workshop](https://ubuntu.com/workshop/docs/) workshop built from
  `.workshop/autowp.yaml`. The Frama-C toolchain comes prebuilt from an SDK;
  nothing is built in the container.
- **B. Multipass (macOS).** Workshop runs only on Linux. On a Mac, create an
  arm64 Ubuntu VM with Multipass and follow A inside it.
- **C. LXD (fallback).** A plain LXD container, in which `frama-c-launch`
  builds the toolchain on its first run (hours). For a Linux host without
  Workshop.

Each way has a step 1 (on the host) and a step 2 (in the container) that end
in a `tmux` session. Step 3, in the harness, is the same for all three and
comes after them. See "The agent harness" below for installation and login.

*Status (2026-11-05): C is the way that has been run end to end. A and B are
designed, and the SDKs they use are built and tested, but no project
generated by `auto-wp.py` has been launched with them yet.*

### A. Workshop (Linux)

You need LXD 6.8 or later and Workshop on the host
(`sudo snap install --channel=6/stable lxd`, or `snap refresh` to that
channel, then `sudo snap install --classic workshop`). amd64 only for now:
the arm64 SDKs are not on the SDK Store yet (see B).

**1. On the host**, in `{{DIR}}`, the directory of this README:

```
workshop launch
workshop shell
```

`workshop launch` reads `.workshop/autowp.yaml`, creates an LXD container
named `autowp`, installs the SDKs it lists (Frama-C 32.1 with WP, macsl,
Why3, Coq 8.20.1 for WP, Alt-Ergo and Z3; Rocq 9.2; Lean 4 with elan, Lake
and lean-lsp-mcp) and this project's own apt packages
(`.workshop/autowp-packages/`), then mounts `{{DIR}}` at `/project`. It
takes minutes, mostly to download the SDKs (about 2 GB). `workshop shell`
opens a shell in `/project` as the user `workshop`, who maps to you, so the
files the agent creates belong to you on the host.

The SDKs come from the SDK Store, channel `latest/edge`, where auto-wp's
builds are released first; nothing else is needed on the host. `workshop
info` shows the status, which is `ready` only when every SDK's health check
passed. If the launch fails, read `workshop changes` and `workshop tasks`,
or run it again with `workshop launch --verbose --wait-on-error`. The
commands above name no workshop, which works while this project has one
definition; if your checkout already has workshops of its own, use
`workshop launch autowp` and `workshop shell autowp`.

**2. In the workshop**, where the shell already is in `/project`: clone the
code, link the Frama-C sources, and start {{HARNESS}} in `tmux`, so the run
goes on when you close the terminal:

```
git clone https://gitlab.freedesktop.org/gnu-grub/grub.git
git config user.name "Your Name"
git config user.email "you@example.com"
git init --bare ~/{{DIR}}.git
git remote add origin ~/{{DIR}}.git
bin/fetch-sources.sh
{{HARNESS_INSTALL}}
. ~/.profile
tmux new -s wp
{{HARNESS_START}}
```

There is no toolchain to build and no `opam init`: the SDK's opam switch is
read-only and ready. `bin/fetch-sources.sh` links `framac-src` to the SDK's
patched Frama-C sources (`FRAMA_C_SDK_SRC`) instead of downloading them,
and clones `macsl/`.

{{HARNESS_LOGIN}}

Alt-Ergo, bundled in the Frama-C SDK, is under the OCamlPro Non-Commercial
Purpose License: research use only (the licence files are in the SDK under
`share/licenses/alt-ergo/`). Without it, WP still has Z3.

Do not run `workshop refresh` or `workshop restore` while a run is going:
they rebuild the container outside `/project` and the SDK mounts, so the
harness login and `~/{{DIR}}.git` are gone afterwards, and the last lines
of step 2 must be run again (`~/.elan` survives: it is a mount of the Lean
SDK).

### B. Multipass (macOS)

Workshop runs only on Linux. On an Apple Silicon Mac, use
[Multipass](https://multipass.run) to create an arm64 Ubuntu VM, install
Workshop in it, and follow A inside it.

*The VM below was created with these values on 2026-11-05; the rest of this
section is designed, not yet run. The arm64 SDKs are built but not yet on
the SDK Store nor tested in a workshop.*

**1. On the Mac:**

```
multipass launch 24.04 --name autowp --cpus 6 --memory 12G --disk 150G
multipass shell autowp
```

Smaller sizes have not been tried. The disk holds the VM's LXD storage pool
for the workshop (the SDKs, the Frama-C sources, the builds of the code
under study), so it is the value to be generous with. **In the VM**, install
LXD 6 (Ubuntu 24.04 images ship LXD as a snap; Workshop needs 6.8 or
later), Workshop and, until the arm64 SDKs are on the Store, sdkcraft:

```
sudo snap refresh lxd --channel=6/stable || sudo snap install lxd --channel=6/stable
sudo lxd init --auto
sudo usermod -aG lxd "$USER"
sudo snap install --classic workshop
sudo snap install --classic sdkcraft
```

then leave the VM shell and open it again, so the group change applies.

Until the arm64 SDKs are on the Store, the VM has to build them: clone the
auto-wp repository (`https://github.com/canonical/awp`) in the VM, run
`sdks/frama-c-sdk/prepare.sh` then `sdkcraft try` in `sdks/frama-c-sdk/`
(hours on the first build), and `sdkcraft try` in `sdks/rocq/` (about an
hour) and `sdks/lean/` (minutes), as its `sdks/README.md` says. Then, in
the VM's copy of this project, replace each Store entry of
`.workshop/autowp.yaml` by its `try-` name without a channel
(`- name: try-frama-c-sdk`, and the same for `rocq` and `lean`). This
paragraph goes away once the arm64 SDKs are published.

**2. Get the project into the VM.** The project must be in the VM's own
filesystem. Either generate it there (`auto-wp.py` runs on Linux), copy a
project generated on the Mac with `multipass transfer -r {{DIR}} autowp:`,
or push it to a remote and clone it in the VM. Do not use `multipass
mount`: Multipass mounts are SSHFS, and a workshop mounting a directory that
is itself an SSHFS mount is unverified and expected to fail. So on macOS the
project and its results live in the VM.

**3. In the VM**, from the project directory, steps 1 and 2 of A. On arm64
the Creusot SDK has no CVC4 and builds Alt-Ergo from opam; the Frama-C side
is the same as on amd64.

**4. Getting results out:** `multipass transfer -r autowp:{{DIR}}/grub.md .`
for a file or a directory, or `git push` of `{{DIR}}` from a VM shell to a
remote you control. The agent's own remote stays the bare repository inside
the workshop.

**5. Keep the Mac awake.** The VM does not run while the Mac sleeps, so a
campaign needs the Mac awake for its whole budget, for example with
`caffeinate -s` in a terminal on the Mac.

*Troubleshooting:* `multipass shell` fails with `ssh connection failed:
'Failed to connect: No route to host'` when run from an SSH session into the
Mac, and works from the Mac's own console (seen 2026-11-05 on macOS 15; the
likely cause is macOS's Local Network privacy setting). Start `tmux` at the
Mac's console and attach to it from the SSH session, or reach the VM
directly with `ssh -J <mac> ubuntu@<vm-ip>` (the IP from `multipass info
autowp`, after adding your public key to the VM's `~/.ssh/authorized_keys`).

### C. LXD (fallback)

You need LXD on the host (`lxc list` works as your user). The toolchain is
built in the container by `frama-c-launch` on the first run, which takes a
few hours of the campaign's budget.

**1. On the host**, run `bin/launch_lxc.sh` from `{{DIR}}`, the directory
of this README:

```
bin/launch_lxc.sh
```

The script finds `{{DIR}}` from its own path, so it also works from any
other directory (`path/to/{{DIR}}/bin/launch_lxc.sh`). It creates the container `wp-{{DIR}}`,
mounts `{{DIR}}` into it, installs the packages the campaign needs, and opens
a shell in it as the user `ubuntu`. It does, in order:

- **Network.** It creates the LXD bridge `lxdbr0` if it does not exist yet,
  and attaches the container to it. Without that, the container gets its
  network from the `default` profile, and on some LXD installs that profile
  has none: `apt-get update` then fails. To use a bridge you already have,
  run `NET=<name> bin/launch_lxc.sh` with a name whose `MANAGED`
  column is `YES` in `lxc network list`.
- **Container.** It launches `ubuntu:24.04` and waits for `cloud-init`, so
  that the container creates `/home/ubuntu` before the mount does. Set
  `CT=<name>` for another container name. If the container already exists,
  the script stops and says how to open a shell in it or delete it.
- **Mount.** It mounts `{{DIR}}` at `/home/ubuntu/{{DIR}}` with
  `shift=true`, which makes your files appear there as owned by the user
  `ubuntu`, and the files the agent creates belong to you on the host.
  Everything the run writes is in `{{DIR}}` on the host as soon as it is
  written.
- **Packages.** git, python3, tmux, curl, opam, and the Frama-C and GRUB
  build dependencies.
- **AppArmor.** It unloads the AppArmor profile that Ubuntu 24.04 ships for
  opam. Inside an LXD container that profile stops opam's downloads from
  opening network sockets, so `opam init` fails with "Could not resolve
  host". A link in `/etc/apparmor.d/disable/` keeps the profile unloaded
  after a restart of the container.

**2. In the container**, clone the code, fetch the Frama-C and macsl sources,
and start {{HARNESS}} in `tmux`, so the run goes on when you close the
terminal:

```
cd {{DIR}}
git clone https://gitlab.freedesktop.org/gnu-grub/grub.git
git config user.name "Your Name"
git config user.email "you@example.com"
git init --bare ~/{{DIR}}.git
git remote add origin ~/{{DIR}}.git
opam init --disable-sandboxing -y --bare
bin/fetch-sources.sh
{{HARNESS_INSTALL}}
. ~/.profile
tmux new -s wp
{{HARNESS_START}}
```

### The agent harness: {{HARNESS}}

### 3. In the harness

Whichever way you took, type:

```
/time-loop grub 72
```

This runs the time-loop campaign on the directory `grub` for 72 hours. Detach
from `tmux` with `Ctrl-b d` and leave the container with `exit`; the run goes
on. To come back to it: with A, `workshop shell` then `tmux attach -t wp`
(with B, after `multipass shell autowp`); with C:

```
lxc exec wp-{{DIR}} -- sudo -iu ubuntu tmux attach -t wp
```

- The source directory `grub/` is kept untouched. Every result is written next
  to it, in `{{DIR}}`, under the prefix `grub-analysis`:
  `grub-analysis-{{DRIVER}}-report.md`, `grub-analysis-found-issues.md`,
  `grub-analysis-acsl/`, and the numbered
  `grub-analysis-{{FEEDBACK}}-NN.md` files.
- The report of the run is written to `grub.md`, next to `grub/`. It is the
  final report when the campaign is finished, or an interim report when the
  deadline is reached first. Each new report replaces the previous one; git
  history keeps the earlier versions.
- You can stop the run and start it again with the same command. The loop
  picks up from its saved state and **keeps the original deadline**:
  `/time-loop grub 72` restarted after 10 hours has 62 hours left, not 72. To
  start a new campaign with a new budget, add `--fresh`.
- With C, on the first run `frama-c-launch` builds the Frama-C toolchain in
  the container. This takes a few hours and counts against the 72. With A
  and B the SDK provides it, and no hour goes to the build.
- The loop commits a checkpoint after every cycle, in `{{DIR}}/.git`, so the
  history is on the host too. It pushes the checkpoint to `~/{{DIR}}.git`, a
  bare repository in the container, so it needs no credentials. With A and
  C the files are on the host through the mount (`/project`, or the LXD
  disk device), so nothing has to be copied out; with B they are in the VM
  (B, step 4).
- The agent can write anything in `{{DIR}}`, including `.git/hooks/`, the
  scripts in `bin/` and the hooks in `.workshop/`. Before you run git or a
  script in `{{DIR}}` on the host, check that `.git/hooks/` holds only
  `*.sample` files and read `git diff` of `bin/`; before the next
  `workshop launch` or `workshop refresh`, read `git diff` of `.workshop/`,
  whose hooks run as root in the container.
- `grub/` is a separate git repository. Git does not track it inside
  `{{DIR}}` unless you add it as a submodule.
- When you are done: with A and B, `workshop remove` removes the workshop
  and the Claude login, and keeps `{{DIR}}`, its results and
  `.workshop/autowp.yaml`. Never delete `{{DIR}}` before `workshop remove`,
  or the workshop is orphaned. `workshop launch` writes `.workshop.lock` in
  `{{DIR}}`; it is in `.gitignore` and must not be copied with the project.
  With C, `lxc delete --force wp-{{DIR}}` removes the container and the
  login, and leaves `{{DIR}}` on the host; the container name `wp-{{DIR}}`
  must contain only letters, digits and hyphens, so pick another name if
  `{{DIR}}` has other characters.

You can also run {{HARNESS}} directly in `{{DIR}}` on the host,
without a container. The agent then acts with all your rights.
{{HARNESS_HOST}}

## Other commands

- `/{{DRIVER}} <dir> <dir>-analysis` — a single campaign (study, onboarding,
  verification) without a time budget.
- `/ebios <dir>` — the same campaign, with an EBIOS Risk Manager risk study
  instead of the `{{DRIVER}}` one.
- `/time-loop` options: `--dir=<subdir>` (focus an existing campaign on a
  subdirectory), `--machdep=<name>` (pin Frama-C's machine model),
  `--linux` and `--full-tu` (Linux kernel profile), `--fresh` (start a new
  campaign), `--no-coq` (skip the Coq-discharge stage). See `config/commands/time-loop.md`
  for details.

## Prerequisites

- **On the host**, one of:
  - *A, Linux (amd64):* LXD 6.8 or later and Workshop
    (`sudo snap install --channel=6/stable lxd`, then
    `sudo snap install --classic workshop`). Nothing else: the SDKs come
    from the SDK Store.
  - *B, macOS:* Multipass on an Apple Silicon Mac. The rest is installed in
    the VM (B, step 1), including, until the arm64 SDKs are published,
    sdkcraft and a clone of the auto-wp repository to build them.
  - *C:* LXD, usable as your user (`lxc list` works), and nothing else.

  This directory is stand-alone: it carries everything the skills need, and
  `bin/fetch-sources.sh` downloads (or, in a workshop, links) the rest. The
  one temporary exception is B until the arm64 SDKs are published.
- **In the container:** {{HARNESS}} (see step 2) and Frama-C 32.1
  with WP and the provers in the `framac-coq8` opam switch. With A and B the
  switch is the one the `frama-c-sdk` SDK ships, read-only under
  `/opt/frama-c-sdk`, with `frama-c`, `why3`, `alt-ergo` and `z3` on `PATH`
  and `FRAMA_C_SDK_SWITCH`, `FRAMA_C_SDK_SRC` and `FRAMA_C_SDK_MACSL` set;
  `frama-c-launch` accepts it on its first run. With C, `frama-c-launch`
  checks the toolchain on the first run, and builds it from `framac-src/`
  (fetched by `bin/fetch-sources.sh`, with `frama-c-patches/` applied) if it
  is missing.
- Optional: `~/.local-llm-machine-ip.txt` in the container, one line with the
  IP address of a local LLM host (for example an ollama server) that the
  container can reach. The cross-provider judge in `sl-auditor` and
  `no_ceiling_gate.py` uses it. Without it, those steps are advisory, and
  `sl-auditor` asks you before going on.

## What is in this directory

- `config/` — the skills (`config/skills/`) and slash commands
  (`config/commands/`), listed in `config/auto-wp.json`.
- `.agents`, `.claude/` and `.opencode/` — links to `config/`, so the agent
  harness (Claude Code, OpenCode, or any harness that reads `.agents/`) finds
  them.
- `.workshop/` — the Workshop definition `autowp.yaml` (way A) and the
  project-local SDK `autowp-packages/`, whose `hooks/setup-base` installs
  the apt packages of the code under study (as generated: GRUB's). Edit it
  for another code base, then `workshop refresh`.
- `bin/` — the scripts the C skills run, always from the project root (for
  example `bin/{{DRIVER}}-lint.sh grub-analysis-{{DRIVER}}-report.md`): the lint checks
  `bin/rmf-lint.sh`, `bin/fips-lint.sh` and `bin/ebios-lint.sh` (the machine gates of `rmf-sl`,
  `fips-sl` and `ebios-sl`), the `bin/framac-*.sh` campaign scripts,
  `bin/ledger-ratchet.sh`, `bin/crosswalk-gen.sh`, `bin/fetch-sources.sh`,
  and `bin/launch_lxc.sh` (step 1 of way C).
- The data those scripts and skills read: the Frama-C patches
  (`frama-c-patches/`), the gold corpus (`framac-gold/`) and `no-ceiling.md`.
- `bin/fetch-sources.sh` downloads the two trees too large to ship here:
  `framac-src/` (Frama-C 32.1, the release archive, with `frama-c-patches/` applied) and
  `macsl/` (the macsl plugin, from GitHub at a fixed commit). In a workshop
  it links `framac-src/` to the SDK's copy instead. `.gitignore` keeps
  both, and `.workshop.lock`, out of the project history.

You can edit the skills in place. The loops add what they learn under
`config/skills/*/getting-better/` and `config/skills/*/references/learned-*.md`.
