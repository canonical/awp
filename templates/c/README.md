# {{DIR}} — automated verification of {{LANGUAGE}} code

This directory was generated by `auto-wp.py`. It is ready to use: clone a code
base into it, start Claude Code in it, and type one command.

## Quick start

The campaign runs for days without asking for permission, so run Claude Code
in an LXD container. The agent can then change only the container and `{{DIR}}`,
which LXD mounts into it: not your other files, not your SSH keys, not your
Claude login. You need LXD on the host
(`lxc list` works as your user).

**1. On the host**, run `bin/launch_lxc.sh` from `{{DIR}}`, the directory
of this README:

```
bin/launch_lxc.sh
```

The script finds `{{DIR}}` from its own path, so it also works from any
other directory (`path/to/{{DIR}}/bin/launch_lxc.sh`). It creates the container `wp-{{DIR}}`,
mounts `{{DIR}}` into it, installs the packages the campaign needs, and opens
a shell in it as the user `ubuntu`. It does, in order:

- **Network.** It creates the LXD bridge `lxdbr0` if it does not exist yet,
  and attaches the container to it. Without that, the container gets its
  network from the `default` profile, and on some LXD installs that profile
  has none: `apt-get update` then fails. To use a bridge you already have,
  run `NET=<name> bin/launch_lxc.sh` with a name whose `MANAGED`
  column is `YES` in `lxc network list`.
- **Container.** It launches `ubuntu:24.04` and waits for `cloud-init`, so
  that the container creates `/home/ubuntu` before the mount does. Set
  `CT=<name>` for another container name. If the container already exists,
  the script stops and says how to open a shell in it or delete it.
- **Mount.** It mounts `{{DIR}}` at `/home/ubuntu/{{DIR}}` with
  `shift=true`, which makes your files appear there as owned by the user
  `ubuntu`, and the files the agent creates belong to you on the host.
  Everything the run writes is in `{{DIR}}` on the host as soon as it is
  written.
- **Packages.** git, python3, tmux, curl, opam, and the Frama-C and GRUB
  build dependencies.
- **AppArmor.** It unloads the AppArmor profile that Ubuntu 24.04 ships for
  opam. Inside an LXD container that profile stops opam's downloads from
  opening network sockets, so `opam init` fails with "Could not resolve
  host". A link in `/etc/apparmor.d/disable/` keeps the profile unloaded
  after a restart of the container.

**2. In the container**, clone the code, fetch the Frama-C and macsl sources,
and start Claude Code in `tmux`, so the run goes on when you close the
terminal:

```
cd {{DIR}}
git clone https://gitlab.freedesktop.org/gnu-grub/grub.git
git config user.name "Your Name"
git config user.email "you@example.com"
git init --bare ~/{{DIR}}.git
git remote add origin ~/{{DIR}}.git
opam init --disable-sandboxing -y --bare
bin/fetch-sources.sh
curl -fsSL https://claude.ai/install.sh | bash
. ~/.profile
tmux new -s wp
claude --dangerously-skip-permissions
```

On the first start, Claude Code asks you to log in: open the URL it prints in
your browser on the host, and paste the code back. The login stays in the
container. Never copy `~/.claude/.credentials.json` from the host into it.

**3. In the harness**, type:

```
/time-loop grub 72
```

This runs the time-loop campaign on the directory `grub` for 72 hours. Detach
from `tmux` with `Ctrl-b d` and leave the container with `exit`; the run goes
on. To come back to it:

```
lxc exec wp-{{DIR}} -- sudo -iu ubuntu tmux attach -t wp
```

- The source directory `grub/` is kept untouched. Every result is written next
  to it, in `{{DIR}}`, under the prefix `grub-analysis`:
  `grub-analysis-rmf-report.md`, `grub-analysis-found-issues.md`,
  `grub-analysis-acsl/`, and the numbered
  `grub-analysis-monitor-feedback-NN.md` files.
- The report of the run is written to `grub.md`, next to `grub/`. It is the
  final report when the campaign is finished, or an interim report when the
  deadline is reached first. Each new report replaces the previous one; git
  history keeps the earlier versions.
- You can stop the run and start it again with the same command. The loop
  picks up from its saved state and **keeps the original deadline**:
  `/time-loop grub 72` restarted after 10 hours has 62 hours left, not 72. To
  start a new campaign with a new budget, add `--fresh`.
- On the first run, `frama-c-launch` builds the Frama-C toolchain in the
  container. This takes a few hours and counts against the 72.
- The loop commits a checkpoint after every cycle, in `{{DIR}}/.git`, so the
  history is on the host too. It pushes the checkpoint to `~/{{DIR}}.git`, a
  bare repository in the container, so it needs no credentials.
- The agent can write anything in `{{DIR}}`, including `.git/hooks/` and the
  scripts in `bin/`. Before you run git or a script in `{{DIR}}` on the host,
  check that `.git/hooks/` holds only `*.sample` files and read `git diff` of
  `bin/`: a hook or script left there would run with your rights.
- `grub/` is a separate git repository. Git does not track it inside
  `{{DIR}}` unless you add it as a submodule.
- When you are done, `lxc delete --force wp-{{DIR}}` removes the container
  and the Claude login. `{{DIR}}` and its results stay on the host.
- The container name `wp-{{DIR}}` must contain only letters, digits and
  hyphens. Pick another name if `{{DIR}}` has other characters.

You can also run `claude` directly in `{{DIR}}` on the host, without a
container. The agent then acts with all your rights, so keep the permission
prompts on (no `--dangerously-skip-permissions`), and the run stops at each
prompt until you answer it.

## Other commands

- `/rmf <dir> <dir>-analysis` — a single campaign (risk study, onboarding,
  verification) without a time budget.
- `/ebios <dir>` — the same campaign, with an EBIOS Risk Manager risk study
  instead of the RMF one.
- `/time-loop` options: `--dir=<subdir>` (focus an existing campaign on a
  subdirectory), `--machdep=<name>` (pin Frama-C's machine model),
  `--linux` and `--full-tu` (Linux kernel profile), `--fresh` (start a new
  campaign), `--no-coq` (skip the Coq-discharge stage). See `config/commands/time-loop.md`
  for details.

## Prerequisites

- **On the host:** LXD, usable as your user (`lxc list` works). Nothing else:
  this directory carries everything the skills need, and step 2 downloads the
  rest.
- **In the container:** Claude Code (installed in step 2), and Frama-C 32.1
  with WP and the provers in the `framac-coq8` opam switch. `frama-c-launch`
  checks the toolchain on the first run, and builds it from `framac-src/`
  (fetched by `bin/fetch-sources.sh`, with `frama-c-patches/` applied) if it is
  missing.
- Optional: `~/.local-llm-machine-ip.txt` in the container, one line with the
  IP address of a local LLM host (for example an ollama server) that the
  container can reach. The cross-provider judge in `sl-auditor` and
  `no_ceiling_gate.py` uses it. Without it, those steps are advisory, and
  `sl-auditor` asks you before going on.

## What is in this directory

- `config/` — the skills (`config/skills/`) and slash commands
  (`config/commands/`), listed in `config/auto-wp.json`.
- `.agents` and `.claude/` — links to `config/`, so the agent harness finds
  them.
- `bin/` — the scripts the C skills run, always from the project root (for
  example `bin/rmf-lint.sh grub-analysis-rmf-report.md`): the lint checks
  `bin/rmf-lint.sh` and `bin/ebios-lint.sh` (the machine gates of `rmf-sl`
  and `ebios-sl`), the `bin/framac-*.sh` campaign scripts,
  `bin/ledger-ratchet.sh`, `bin/crosswalk-gen.sh`, `bin/fetch-sources.sh`,
  and `bin/launch_lxc.sh` (step 1 of the quick start).
- The data those scripts and skills read: the Frama-C patches
  (`frama-c-patches/`), the gold corpus (`framac-gold/`) and `no-ceiling.md`.
- `bin/fetch-sources.sh` downloads the two trees too large to ship here:
  `framac-src/` (Frama-C 32.1, the release archive, with `frama-c-patches/` applied) and
  `macsl/` (the macsl plugin, from GitHub at a fixed commit). `.gitignore`
  keeps both out of the project history.

You can edit the skills in place. The loops add what they learn under
`config/skills/*/getting-better/` and `config/skills/*/references/learned-*.md`.
