# {{DIR}} — automated verification of {{LANGUAGE}} code

This directory was generated by `auto-wp.py`. It is ready to use: clone a
crate into it, start Claude Code in it, and make one request.

## Quick start

The loops run for hours without asking for permission, so run Claude Code in
an LXD container. The agent can then change only the container and `{{DIR}}`,
which LXD mounts into it: not your other files, not your SSH keys, not your
Claude login. You need LXD on the host
(`lxc list` works as your user).

**1. On the host**, in `{{DIR}}`, the directory of this README: go up to
its parent, create the container and mount `{{DIR}}` into it. The mount
line uses `$PWD/{{DIR}}`, so the commands must run from the parent, which
the first line does:

```
cd ..
CT=wp-{{DIR}}
NET=lxdbr0
lxc network show "$NET" >/dev/null 2>&1 || lxc network create "$NET"
lxc launch ubuntu:24.04 "$CT" --network "$NET"
lxc exec "$CT" -- cloud-init status --wait
lxc config device add "$CT" {{DIR}} disk source="$PWD/{{DIR}}" \
    path=/home/ubuntu/{{DIR}} shift=true
lxc exec "$CT" --env DEBIAN_FRONTEND=noninteractive -- sh -c 'apt-get update &&
    apt-get install -y git python3 tmux curl opam build-essential pkg-config \
    libcairo2-dev libgtk-3-dev libgtksourceview-3.0-dev libgmp-dev \
    zlib1g-dev unzip m4'
lxc exec "$CT" -- sh -c 'ln -s /etc/apparmor.d/opam /etc/apparmor.d/disable/ &&
    apparmor_parser -R /etc/apparmor.d/opam'
lxc exec "$CT" -- sudo -iu ubuntu
```

`NET` is the LXD bridge that gives the container its network access. The
second line creates the bridge `lxdbr0` if it does not exist yet; to use a
bridge you already have, set `NET` to a name whose `MANAGED` column is `YES`
in `lxc network list`. Without `--network`, the container gets its network
from the `default` profile, and on some LXD installs that profile has none:
`apt-get update` then fails.

The `lxc config device add` line mounts `{{DIR}}` at `/home/ubuntu/{{DIR}}`
in the container. `shift=true` makes your files appear there as owned by the
user `ubuntu`, and the files the agent creates belong to you on the host.
Everything the run writes is in `{{DIR}}` on the host as soon as it is
written. `cloud-init status --wait` waits until the container has created
`/home/ubuntu`, so that the mount does not create it first.

The `apparmor_parser` line unloads the AppArmor profile that Ubuntu 24.04
ships for opam. Inside an LXD container that profile stops opam's downloads
from opening network sockets, so `opam init` fails with "Could not resolve
host". The link keeps the profile unloaded after a restart of the container.

The last command opens a shell as the user `ubuntu` in the container.

**2. In the container**, install Rust and Creusot (this takes an hour or
more), clone the crate, and start Claude Code in `tmux`, so the run goes on
when you close the terminal:

```
opam init --disable-sandboxing -y --bare
curl -sSf https://sh.rustup.rs | sh -s -- -y
. ~/.cargo/env
git clone https://github.com/creusot-rs/creusot.git ~/git/creusot
(cd ~/git/creusot && ./INSTALL)
cd {{DIR}}
git clone <crate-url> mycrate
git config user.name "Your Name"
git config user.email "you@example.com"
git init --bare ~/{{DIR}}.git
git remote add origin ~/{{DIR}}.git
curl -fsSL https://claude.ai/install.sh | bash
. ~/.profile
tmux new -s wp
claude --dangerously-skip-permissions
```

On the first start, Claude Code asks you to log in: open the URL it prints in
your browser on the host, and paste the code back. The login stays in the
container. Never copy `~/.claude/.credentials.json` from the host into it.

**3. In the harness**, ask:

```
onboard the crate mycrate with creusot-launch, then analyze it with creusot-monitoring
```

`creusot-launch` prepares the crate for Creusot and hands it to
`creusot-monitoring`, which verifies it file by file with the `creusot-sl`
loop. Detach from `tmux` with `Ctrl-b d` and leave the container with `exit`;
the run goes on. To come back to it:

```
lxc exec wp-{{DIR}} -- sudo -iu ubuntu tmux attach -t wp
```

- The crate `mycrate/` is kept untouched. The annotated copy lives in an
  overlay next to it, `mycrate-creusot/`, and every other result is written in
  `{{DIR}}`.
- Commits are made in `{{DIR}}/.git`, so the history is on the host too. They
  are pushed to `~/{{DIR}}.git`, a bare repository in the container, so the
  container needs no credentials.
- The agent can write anything in `{{DIR}}`, including `.git/hooks/`. Before
  you run git or a script in `{{DIR}}` on the host, check that `.git/hooks/`
  holds only `*.sample` files: a hook left there would run with your rights.
- `mycrate/` is a separate git repository. Git does not track it inside
  `{{DIR}}` unless you add it as a submodule.
- Do not create `{{DIR}}` inside a Cargo project, and keep the crate next to
  its overlay, not under it: `cargo creusot new` writes `why3find.json` next
  to the nearest parent `Cargo.toml`, which would put it in the wrong place.
- When you are done, `lxc delete --force wp-{{DIR}}` removes the container
  and the Claude login. `{{DIR}}` and its results stay on the host.
- The container name `wp-{{DIR}}` must contain only letters, digits and
  hyphens. Pick another name if `{{DIR}}` has other characters.

You can also run `claude` directly in `{{DIR}}` on the host, without a
container. The agent then acts with all your rights, so keep the permission
prompts on (no `--dangerously-skip-permissions`), and the run stops at each
prompt until you answer it.

## Other commands

There are no slash commands for Rust yet (`config/commands/` is empty). Ask
for these skills by name instead:

- `creusot-launch` — onboard a crate: build configuration, toolchain check,
  overlay, scope map, smoke proof.
- `creusot-monitoring` — verify a whole crate, file by file, leaf files first.
- `creusot-sl` — verify one `*.rs` file.
- `creusot` — the Pearlite reference used by the other skills.

## Prerequisites

- **On the host:** LXD, usable as your user (`lxc list` works).
- **In the container** (installed in step 2): Claude Code, Creusot
  (`cargo creusot`), Why3, why3find, the solvers (Alt-Ergo, Z3, CVC4, CVC5),
  and the nightly Rust toolchain pinned by Creusot. `creusot-launch` checks
  them but does not install them. The Creusot checkout (`~/git/creusot`) must
  stay where it was installed from, because its installer points
  `~/.cargo/config.toml` at it.
- No `use-frama-c` checkout is needed.
- Optional: `~/.local-llm-machine-ip.txt` in the container, one line with the
  IP address of a local LLM host (for example an ollama server) that the
  container can reach, for a cross-provider judge.
  The C versions of `sl-auditor` and `no_ceiling_gate.py` use it; the Creusot
  versions installed here do not read it yet, so their audit steps rely on a
  cross-provider or human reviewer that you provide.

## What is in this directory

- `config/` — the skills (`config/skills/`) and slash commands
  (`config/commands/`, empty for now), listed in `config/auto-wp.json`.
- `.agents` and `.claude/` — links to `config/`, so the agent harness finds
  them.

You can edit the skills in place. The loops add what they learn under
`config/skills/*/getting-better/` and `config/skills/*/references/learned-*.md`.
