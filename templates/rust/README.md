# {{DIR}} — automated verification of {{LANGUAGE}} code

This directory was generated by `auto-wp.py`. It is ready to use: clone a
crate into it, start Claude Code in it, and make one request.

## Quick start

The loops run for hours without asking for permission, so run Claude Code in
a container. The agent can then change only the container and `{{DIR}}`,
which is mounted into it: not your other files, not your SSH keys, not your
Claude login. There are three ways to get that container; follow one:

- **A. Workshop (Linux).** The container is a
  [Workshop](https://ubuntu.com/workshop/docs/) workshop built from
  `.workshop/autowp.yaml`. Creusot comes prebuilt from an SDK; nothing is
  built in the container.
- **B. Multipass (macOS).** Workshop runs only on Linux. On a Mac, create an
  arm64 Ubuntu VM with Multipass and follow A inside it.
- **C. LXD (fallback).** A plain LXD container, in which you install Rust
  and Creusot by hand (an hour or more). For a Linux host without Workshop.

Each way has a step 1 (on the host) and a step 2 (in the container) that end
with `claude --dangerously-skip-permissions`. Step 3, in the harness, is the
same for all three and comes after them.

*Status (2026-11-05): C is the way that has been run end to end. A and B are
designed, and the SDKs they use are built and tested, but no project
generated by `auto-wp.py` has been launched with them yet.*

### A. Workshop (Linux)

You need LXD 6.8 or later and Workshop on the host
(`sudo snap install --channel=6/stable lxd`, or `snap refresh` to that
channel, then `sudo snap install --classic workshop`). amd64 only for now:
the arm64 SDKs are not on the SDK Store yet (see B).

**1. On the host**, in `{{DIR}}`, the directory of this README:

```
workshop launch
workshop shell
```

`workshop launch` reads `.workshop/autowp.yaml`, creates an LXD container
named `autowp`, installs the SDKs it lists (Creusot at commit `f15b985`
with its Rust nightly, Why3, why3find, Alt-Ergo, Z3, CVC4 and CVC5; Rocq
9.2; Lean 4 with elan, Lake and lean-lsp-mcp) and this project's own apt
packages (`.workshop/autowp-packages/`), then mounts `{{DIR}}` at
`/project`. It takes minutes, mostly to download the SDKs (about 1.5 GB).
`workshop shell` opens a shell in `/project` as the user `workshop`, who
maps to you, so the files the agent creates belong to you on the host.

The SDKs come from the SDK Store, channel `latest/edge`, where auto-wp's
builds are released first; nothing else is needed on the host. `workshop
info` shows the status, which is `ready` only when every SDK's health check
passed. If the launch fails, read `workshop changes` and `workshop tasks`,
or run it again with `workshop launch --verbose --wait-on-error`. The
commands above name no workshop, which works while this project has one
definition; if your checkout already has workshops of its own, use
`workshop launch autowp` and `workshop shell autowp`.

**2. In the workshop**, where the shell already is in `/project`: clone the
crate and start Claude Code in `tmux`, so the run goes on when you close the
terminal:

```
git clone <crate-url> mycrate
git config user.name "Your Name"
git config user.email "you@example.com"
git init --bare ~/{{DIR}}.git
git remote add origin ~/{{DIR}}.git
curl -fsSL https://claude.ai/install.sh | bash
. ~/.profile
tmux new -s wp
claude --dangerously-skip-permissions
```

There is nothing to install: `cargo creusot` is on `PATH`, rustup and Cargo
are in `~/.rustup` and `~/.cargo`, seeded by the SDK and kept across
refreshes, and `~/.cargo/config.toml` already points `creusot-std` at the
SDK's Creusot sources.

On the first start, Claude Code asks you to log in: open the URL it prints in
your browser on the host, and paste the code back. The login stays in the
workshop. Never copy `~/.claude/.credentials.json` from the host into it.

Alt-Ergo, bundled in the Creusot SDK, is under the OCamlPro Non-Commercial
Purpose License: research use only (the licence files are in the SDK under
`share/licenses/alt-ergo/`). Without it, Creusot still has Z3, CVC4 and
CVC5; a commercial user removes Alt-Ergo from the strategy in the project's
`why3find.json`.

Do not run `workshop refresh` or `workshop restore` while a run is going:
they rebuild the container outside `/project` and the SDK mounts, so Claude
Code, its login and `~/{{DIR}}.git` are gone afterwards, and the last lines
of step 2 must be run again (`~/.cargo`, `~/.rustup` and `~/.elan` survive:
they are mounts of the SDKs).

### B. Multipass (macOS)

Workshop runs only on Linux. On an Apple Silicon Mac, use
[Multipass](https://multipass.run) to create an arm64 Ubuntu VM, install
Workshop in it, and follow A inside it.

*The VM below was created with these values on 2026-11-05; the rest of this
section is designed, not yet run. The arm64 SDKs are built but not yet on
the SDK Store nor tested in a workshop.*

**1. On the Mac:**

```
multipass launch 24.04 --name autowp --cpus 6 --memory 12G --disk 150G
multipass shell autowp
```

Smaller sizes have not been tried. The disk holds the VM's LXD storage pool
for the workshop (the SDKs and the builds of the crate under study), so it
is the value to be generous with. **In the VM**, install LXD 6 (Ubuntu
24.04 images ship LXD as a snap; Workshop needs 6.8 or later), Workshop
and, until the arm64 SDKs are on the Store, sdkcraft:

```
sudo snap refresh lxd --channel=6/stable || sudo snap install lxd --channel=6/stable
sudo lxd init --auto
sudo usermod -aG lxd "$USER"
sudo snap install --classic workshop
sudo snap install --classic sdkcraft
```

then leave the VM shell and open it again, so the group change applies.

Until the arm64 SDKs are on the Store, the VM has to build them: clone the
auto-wp repository (`https://github.com/canonical/awp`) in the VM, run
`sdkcraft try` in `sdks/creusot/` (about 40 minutes), `sdks/rocq/` (about
an hour) and `sdks/lean/` (minutes), as its `sdks/README.md` says. Then, in
the VM's copy of this project, replace each Store entry of
`.workshop/autowp.yaml` by its `try-` name without a channel
(`- name: try-creusot`, and the same for `rocq` and `lean`). This paragraph
goes away once the arm64 SDKs are published.

**2. Get the project into the VM.** The project must be in the VM's own
filesystem. Either generate it there (`auto-wp.py` runs on Linux), copy a
project generated on the Mac with `multipass transfer -r {{DIR}} autowp:`,
or push it to a remote and clone it in the VM. Do not use `multipass
mount`: Multipass mounts are SSHFS, and a workshop mounting a directory that
is itself an SSHFS mount is unverified and expected to fail. So on macOS the
project and its results live in the VM.

**3. In the VM**, from the project directory, steps 1 and 2 of A. On arm64
the Creusot SDK ships no CVC4 (no arm64 build exists) and builds Alt-Ergo
from opam, so proofs use Alt-Ergo, Z3 and CVC5.

**4. Getting results out:** `multipass transfer -r autowp:{{DIR}}/mycrate-creusot .`
for a file or a directory, or `git push` of `{{DIR}}` from a VM shell to a
remote you control. The agent's own remote stays the bare repository inside
the workshop.

**5. Keep the Mac awake.** The VM does not run while the Mac sleeps, so a
long run needs the Mac awake for its whole duration, for example with
`caffeinate -s` in a terminal on the Mac.

*Troubleshooting:* `multipass shell` fails with `ssh connection failed:
'Failed to connect: No route to host'` when run from an SSH session into the
Mac, and works from the Mac's own console (seen 2026-11-05 on macOS 15; the
likely cause is macOS's Local Network privacy setting). Start `tmux` at the
Mac's console and attach to it from the SSH session, or reach the VM
directly with `ssh -J <mac> ubuntu@<vm-ip>` (the IP from `multipass info
autowp`, after adding your public key to the VM's `~/.ssh/authorized_keys`).

### C. LXD (fallback)

You need LXD on the host (`lxc list` works as your user).

**1. On the host**, in `{{DIR}}`, the directory of this README: go up to
its parent, create the container and mount `{{DIR}}` into it. The mount
line uses `$PWD/{{DIR}}`, so the commands must run from the parent, which
the first line does:

```
cd ..
CT=wp-{{DIR}}
NET=lxdbr0
lxc network show "$NET" >/dev/null 2>&1 || lxc network create "$NET"
lxc launch ubuntu:24.04 "$CT" --network "$NET"
lxc exec "$CT" -- cloud-init status --wait
lxc config device add "$CT" {{DIR}} disk source="$PWD/{{DIR}}" \
    path=/home/ubuntu/{{DIR}} shift=true
lxc exec "$CT" --env DEBIAN_FRONTEND=noninteractive -- sh -c 'apt-get update &&
    apt-get install -y git python3 tmux curl opam build-essential pkg-config \
    libcairo2-dev libgtk-3-dev libgtksourceview-3.0-dev libgmp-dev \
    zlib1g-dev unzip m4'
lxc exec "$CT" -- sh -c 'ln -s /etc/apparmor.d/opam /etc/apparmor.d/disable/ &&
    apparmor_parser -R /etc/apparmor.d/opam'
lxc exec "$CT" -- sudo -iu ubuntu
```

`NET` is the LXD bridge that gives the container its network access. The
second line creates the bridge `lxdbr0` if it does not exist yet; to use a
bridge you already have, set `NET` to a name whose `MANAGED` column is `YES`
in `lxc network list`. Without `--network`, the container gets its network
from the `default` profile, and on some LXD installs that profile has none:
`apt-get update` then fails.

The `lxc config device add` line mounts `{{DIR}}` at `/home/ubuntu/{{DIR}}`
in the container. `shift=true` makes your files appear there as owned by the
user `ubuntu`, and the files the agent creates belong to you on the host.
Everything the run writes is in `{{DIR}}` on the host as soon as it is
written. `cloud-init status --wait` waits until the container has created
`/home/ubuntu`, so that the mount does not create it first.

The `apparmor_parser` line unloads the AppArmor profile that Ubuntu 24.04
ships for opam. Inside an LXD container that profile stops opam's downloads
from opening network sockets, so `opam init` fails with "Could not resolve
host". The link keeps the profile unloaded after a restart of the container.

The last command opens a shell as the user `ubuntu` in the container.

**2. In the container**, install Rust and Creusot (this takes an hour or
more), clone the crate, and start Claude Code in `tmux`, so the run goes on
when you close the terminal:

```
opam init --disable-sandboxing -y --bare
curl -sSf https://sh.rustup.rs | sh -s -- -y
. ~/.cargo/env
git clone https://github.com/creusot-rs/creusot.git ~/git/creusot
(cd ~/git/creusot && ./INSTALL)
cd {{DIR}}
git clone <crate-url> mycrate
git config user.name "Your Name"
git config user.email "you@example.com"
git init --bare ~/{{DIR}}.git
git remote add origin ~/{{DIR}}.git
curl -fsSL https://claude.ai/install.sh | bash
. ~/.profile
tmux new -s wp
claude --dangerously-skip-permissions
```

On the first start, Claude Code asks you to log in: open the URL it prints in
your browser on the host, and paste the code back. The login stays in the
container. Never copy `~/.claude/.credentials.json` from the host into it.

### 3. In the harness

Whichever way you took, ask:

```
onboard the crate mycrate with creusot-launch, then analyze it with creusot-monitoring
```

`creusot-launch` prepares the crate for Creusot and hands it to
`creusot-monitoring`, which verifies it file by file with the `creusot-sl`
loop. Detach from `tmux` with `Ctrl-b d` and leave the container with `exit`;
the run goes on. To come back to it: with A, `workshop shell` then
`tmux attach -t wp` (with B, after `multipass shell autowp`); with C:

```
lxc exec wp-{{DIR}} -- sudo -iu ubuntu tmux attach -t wp
```

- The crate `mycrate/` is kept untouched. The annotated copy lives in an
  overlay next to it, `mycrate-creusot/`, and every other result is written in
  `{{DIR}}`.
- Commits are made in `{{DIR}}/.git`, so the history is on the host too. They
  are pushed to `~/{{DIR}}.git`, a bare repository in the container, so the
  container needs no credentials. With A and C the files are on the host
  through the mount (`/project`, or the LXD disk device); with B they are
  in the VM (B, step 4).
- The agent can write anything in `{{DIR}}`, including `.git/hooks/` and the
  hooks in `.workshop/`. Before you run git or a script in `{{DIR}}` on the
  host, check that `.git/hooks/` holds only `*.sample` files; before the
  next `workshop launch` or `workshop refresh`, read `git diff` of
  `.workshop/`, whose hooks run as root in the container.
- `mycrate/` is a separate git repository. Git does not track it inside
  `{{DIR}}` unless you add it as a submodule.
- Do not create `{{DIR}}` inside a Cargo project, and keep the crate next to
  its overlay, not under it: `cargo creusot new` writes `why3find.json` next
  to the nearest parent `Cargo.toml`, which would put it in the wrong place.
- When you are done: with A and B, `workshop remove` removes the workshop
  and the Claude login, and keeps `{{DIR}}`, its results and
  `.workshop/autowp.yaml`. Never delete `{{DIR}}` before `workshop remove`,
  or the workshop is orphaned. `workshop launch` writes `.workshop.lock` in
  `{{DIR}}`; it is in `.gitignore` and must not be copied with the project.
  With C, `lxc delete --force wp-{{DIR}}` removes the container and the
  login, and leaves `{{DIR}}` on the host; the container name `wp-{{DIR}}`
  must contain only letters, digits and hyphens, so pick another name if
  `{{DIR}}` has other characters.

You can also run `claude` directly in `{{DIR}}` on the host, without a
container. The agent then acts with all your rights, so keep the permission
prompts on (no `--dangerously-skip-permissions`), and the run stops at each
prompt until you answer it.

## Other commands

There are no slash commands for Rust yet (`config/commands/` is empty). Ask
for these skills by name instead:

- `creusot-launch` — onboard a crate: build configuration, toolchain check,
  overlay, scope map, smoke proof.
- `creusot-monitoring` — verify a whole crate, file by file, leaf files first.
- `creusot-sl` — verify one `*.rs` file.
- `creusot` — the Pearlite reference used by the other skills.

## Prerequisites

- **On the host**, one of:
  - *A, Linux (amd64):* LXD 6.8 or later and Workshop
    (`sudo snap install --channel=6/stable lxd`, then
    `sudo snap install --classic workshop`). Nothing else: the SDKs come
    from the SDK Store.
  - *B, macOS:* Multipass on an Apple Silicon Mac. The rest is installed in
    the VM (B, step 1), including, until the arm64 SDKs are published,
    sdkcraft and a clone of the auto-wp repository to build them.
  - *C:* LXD, usable as your user (`lxc list` works), and nothing else.

  This directory is stand-alone. The one temporary exception is B until the
  arm64 SDKs are published.
- **In the container:** Claude Code (installed in step 2), Creusot
  (`cargo creusot`), Why3, why3find, the solvers (Alt-Ergo, Z3, CVC4, CVC5)
  and the nightly Rust toolchain pinned by Creusot. With A and B they come
  from the `creusot` SDK (`cargo creusot` on `PATH`, `CREUSOT_SDK_SRC` and
  `CREUSOT_SDK_COMMIT` set, `~/.cargo` and `~/.rustup` seeded and kept
  across refreshes); with C you install them in step 2. `creusot-launch`
  checks them but does not install them. With C, the Creusot checkout
  (`~/git/creusot`) must stay where it was installed from, because its
  installer points `~/.cargo/config.toml` at it.
- No `use-frama-c` checkout is needed.
- Optional: `~/.local-llm-machine-ip.txt` in the container, one line with the
  IP address of a local LLM host (for example an ollama server) that the
  container can reach, for a cross-provider judge.
  The C versions of `sl-auditor` and `no_ceiling_gate.py` use it; the Creusot
  versions installed here do not read it yet, so their audit steps rely on a
  cross-provider or human reviewer that you provide.

## What is in this directory

- `config/` — the skills (`config/skills/`) and slash commands
  (`config/commands/`, empty for now), listed in `config/auto-wp.json`.
- `.agents` and `.claude/` — links to `config/`, so the agent harness finds
  them.
- `.workshop/` — the Workshop definition `autowp.yaml` (way A) and the
  project-local SDK `autowp-packages/`, whose `hooks/setup-base` installs
  `tmux` and `curl` and is where the crate's own apt packages go (then
  `workshop refresh`).
- `.gitignore` — keeps `.workshop.lock`, written by `workshop launch`, out
  of the project history.

You can edit the skills in place. The loops add what they learn under
`config/skills/*/getting-better/` and `config/skills/*/references/learned-*.md`.
